# Pilot evidence — pdlc + Orca, 2026-11-07

Read this when the skill's behaviour surprises you, or before changing the guard.
Everything below was measured on this machine with Orca's CLI and pdlc 1.2.0 +
the 1.3.0 work in flight.

## The `hide` trap

`orca repo add` registers the repo with `"externalWorktreeVisibility": "hide"`.
In that mode, run from inside a worktree pdlc created:

```text
$ orca worktree current --json
result.worktree.path   = /Users/…/pdlc          # the MAIN worktree
result.worktree.branch = refs/heads/main
ok                     = true
```

No error. A `cd`-based agent would work in `main`.

With the override:

```bash
orca repo set --repo "path:/Users/…/pdlc" --external-worktree-visibility show
```

the same command resolves the pdlc worktree:

```text
path   = /Users/…/pdlc/.lane/trees/pdlc-105-spec-declaration-wrap
branch = refs/heads/pdlc/pdlc-105-spec-declaration-wrap
isMainWorktree = false
```

`show` is a per-repo override of a global default; `inherit` clears it. The
setting is listed by `orca repo show --repo path:<repo> --json`.

## Worktrees outside the repo root are invisible

A git worktree created under `/var/folders/…` (outside the registered repo
root) made `orca worktree current` fail outright. The same worktree recreated
at `.lane/trees/guard-probe` resolved normally. pdlc's default `trees_dir` is
inside the repo, so the normal flow is fine; a custom `trees_dir` outside it
is not.

## Identity worth recording

From `orca worktree current --json`:

| Field | Example | Use |
| --- | --- | --- |
| `id` | `76dc5d41-…::/Users/…/.lane/trees/<slug>` | addresses the workspace; **contains the local path**, so do not put it in the run record |
| `identity.key` | `wt2:local:03dc13e0-…` | path-free; the right reference for a report |
| `branch` | `refs/heads/pdlc/<slug>` | what the guard compares |
| `head` | `af2290e…` | the commit pdlc dispatched from |

Terminals carry handles like `term_018edcc0-…`; OpenCode sessions `ses_…`.

## What the merge does

`pdlc merge` prunes `.lane/trees/<slug>` and deletes the branch. Orca then
drops the workspace from `worktree list` **and** its terminals go `exited` — both
observed. That is a side effect, not a contract: close the terminals you opened
before merging, or a live agent loses its cwd mid-run.

## Agent failures stay clean

`opencode run` hit `provider.go-limit` (HTTP 429) on a rework. The pdlc state
after the failure:

- `runs.json`: same `run_id`, `status: active`, `head_commit: null`;
- `attempts.json`: `attempts: 1`, unchanged;
- no commit, worktree clean.

Resuming the same session with another model worked:

```bash
opencode run --session ses_… --model agentworks/deepseek-v4-1-flash \
  --agent worker --auto --format json "…"
```

A new session would have produced a second execution that never happened.

## Forge import (Gate 4)

`forge db import-record <record> --source pdlc --task <forge-task-id> --space pdlc`
imported and was idempotent (`already present` on the second run), with the event
log recording `externalRunId`. Reported gaps:

```text
pipeline_revision, skills, models, context_hash, prompt_hash, interventions, cost
```

Two things that look like bugs and are not:

- `task "PDLC-105" not found`: Forge's contract says the external task id is
  provenance, "never matched against a Forge task id" (`pdlc-integration.md` §2).
  The importer names a Forge Task; the mapping is the caller's job.
- `base none` in `task resume`: Forge's Run row has no commit columns; the base
  and head live in the stored external record.

`models` is the one gap this integration closes: pdlc-107 adds
`pdlc exec <slug> --role … --model …` writing `models: [{role, model}]` after
the 1.3.0 cut.
